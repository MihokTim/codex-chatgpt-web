- 起動待ちの進捗をトークン取得前にも配信し、子チャットの識別名を補います。未送信の処理は最後の購読元が切断された際に整理し、送信済み処理の再接続は保持します。

## 配布元がずれた原因と防止

別worktreeの修正を配布した後、元の作業フォルダーとローカルmainを更新していなかったため、実行環境より古いソースが残っていました。
バージョン文字列だけでは同じ6.1.1の異なるforkを区別できません。

配布時は以下を一組として確認します。

1. ローカル変更を検証・コミットし、配布元をクリーンにする。
2. 対象の作業フォルダーとGitHubの配布ブランチを同一コミットにfast-forwardする。
3. `CODEX_CHATGPT_WEB_REQUIRE_CLEAN_SOURCE=1` でそのコミットからビルドする。
4. アイドル時にバックアップを取り、通常終了してから配布物を入れ替える。
5. `node scripts/verify-deployment.cjs <spec.json>` で実際のGitHub refs、作業フォルダー、配布物の全ハッシュを照合する。
6. 実行中プロセスのバージョン・起動元・ヘルスを別途確認する。ディスク一致だけを実行中コードの一致と見なさない。

specの形式:

```json
{
  "repository": "配布元リポジトリの絶対パス",
  "checkouts": ["他の同期対象作業フォルダーの絶対パス"],
  "remote": "origin",
  "branches": ["main", "codex/model-controls-repair", "codex/broker-orca-integration"],
  "runtimes": ["アプリ内resources/runtimeの絶対パス", "実行用versionsディレクトリの絶対パス"]
}
```

ビルド来歴の入力にはランタイムだけでなくlauncherのソース・Electron処理・アセット・ビルドスクリプトも含めます。
確認スクリプトは読み取り専用で、不一致を検出した場合に自動上書き・強制pushはしません。

## 検証範囲

Windows上でフック移行・再設定・解除・改変拒否・書き込み失敗時の復旧、ブローカー、Zero Risk起動失敗、配布物照合、更新進捗の回帰テストを実行しています。
シンボリックリンク等の環境依存テストは条件付きskipです。インストーラーのPowerShell実行テストは端末のExecutionPolicyで拒否されるため、ポリシーを迂回していません。
高コストのWeb/Astra/Proを使った再現試験は実施していません。MCPの確認は推論を開始しないapp-serverセッションで行います。
Orcaの構造化worker起動が受付未確認になる問題や、巨大な会話履歴の圧縮時間そのものを、この修正で解決したとは扱いません。
