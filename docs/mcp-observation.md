# MCP受信の診断ログ

MCPプロセスは、標準エラー出力に加えて、アプリケーションhome内の `diagnostics/mcp/mcp-<pid>-<ランダムID>.jsonl` にUTF-8の受信・応答メタデータを保存する。通常のhomeは `%USERPROFILE%\.codex-chatgpt-web`。`CODEX_CHATGPT_WEB_HOME` を指定した実行では、そのhomeを使用する。

これは受信状況の観測機能であり、ツールの認証、承認、公開schema、annotation、実行結果を変更しない。コマンド・引数・トークン・ファイルパス・生のrequest ID・結果本文・任意のエラー文字列は保存しない。ログ保存先の問題は元のツール応答を失敗に変えない。

## イベントと判定範囲

| イベント | 示すこと |
|---|---|
| `observation_started` | そのプロセスが専用ログの記録を開始した。接続・認証・実行の成功は示さない |
| `call_received` | MCP transportでtools/callを受信した。schema検証より前の記録 |
| `reply_sent` | MCP応答を送信した。`is_error`も確認する。Windowsコマンド実行の成功と同義ではない |
| `reply_send_failed` | MCP応答の送信が失敗した。実行を取り消したことや未実行は意味しない |
| `uncorrelated_call` | 重複IDまたは追跡上限のため、正確な対応付けを行わない |
| `transport_closed` | transportの終了通知を観測した。終了方法によってはこの通知が来ない場合もある |
| `observation_stopped` | ファイルの上限に達し、以降の専用ファイル記録を停止した |
| `observation_unavailable` | 専用ファイルの開始・書込に失敗した。標準エラーにだけ出る場合がある |

各レコードにはUTC時刻、pid、プロセス内の連番がある。受信と応答は `call` で照合する。重複IDの場合は、同IDの全未応答が完了するまで新しい相関を開始しない。送信待機中に重複受信した場合も、古い応答を新しい要求へ対応付けない。

専用ファイルの上限はプロセスあたり1 MiB。上限に達した際は停止マーカーを残し、既存の証拠を上書きしない。標準エラー出力は継続する。新しいMCPプロセスは別ファイルを作る。全プロセスを合計した保存容量や保存日数を制限する機能ではない。

## 拒否を調べる際の注意

`call_received` がないことだけで、サービス側で拒否されたと断定しない。修正版のMCPプロセスが動いていること、対象時刻・pid・連番、上限停止やログ欠落、並行処理を確認する。クラッシュ時の欠落や不完全な最終行も区別する。

`call_received → reply_sent(is_error=true)` があっても、schemaエラー・実行前エラー・ツール内のエラーは別である。既存のbrokerのqueued/delivered/completedと、実際のツール結果を対応させる。OpenAI内部の安全性判定理由は、このログだけでは分からない。

受信した拒否を成功へ書き換えたり、別のツール・モデルで拒否された操作を代行したり、自動再送したりする機能はない。

## 適用と検証

この機能は修正版CLIから新たに起動したMCPプロセスに適用される。リポジトリの変更や候補バンドルの作成だけでは、稼働中の旧MCPプロセスへ反映されない。通常の配備手順で修正版を配置し、処理中のチャットがないことを確認して正常な再起動を行う。調査中の接続を切断して反映したと扱わない。

回帰テスト:

```powershell
bun test tests/mcp-observation.test.ts tests/mcp-observation-log.test.ts
```

実stdioのテストは隔離homeと不正なfixture引数を使用する。MCPのschema検証でエラーになる要求でも受信・応答を記録し、実broker・認証情報・実コマンド実行へ到達しないことを確認する。これはOpenAIからの実接続で安全性拒否が解消した証拠ではない。
