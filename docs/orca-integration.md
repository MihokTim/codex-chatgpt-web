# Orcaとの連携手順

この文書は導入・受入確認の手順。手順の存在だけで相互運用成功を示すものではない。
実行結果はローカルの検証記録に残し、未実施の工程を成功扱いしない。

## 2026-09-27の確認結果

- Windows安定版Orca 1.4.215とClaude Code 2.1.274を公式配布物から導入した。配布ハッシュと署名を確認済み。
- Orcaのdesktop/runtimeが起動し、CLI接続が成立した。
- Orcaの通常のPowerShellターミナルからCodex 0.153.4を起動し、`gpt-6-astra`でローカルfixtureの読取りツールと最終回答を確認した。保存された実行コンテキストでも同じモデルを確認した。
- このWindows環境ではOrcaのターミナルが別のCodex homeを継承した。単独・協業試験では子プロセスの`CODEX_HOME`に既存の保存先を明示した。全体の既定モデルは変更していない。
- Claude/Opusは契約前のためユーザー指示で保留。ログイン待ちプロセスも終了した。インストール済みであることと利用可能であることを区別する。
- Astra親とGPT-5.6 Pro Web子で5件のTaskを実行。fixture読取り、同じ端末への追加依頼、意図したファイル不在エラーの失敗通知、独立企画案、相互批評を確認した。失敗通知の試験は合格したが、元のTaskは正しく`failed`であり、成功に書き換えていない。
- 標準Codex homeに保存された両セッションの実行コンテキストで、親`gpt-6-astra`/high、子`chatgpt-web/gpt-5.6-pro`/maxを確認した。Web担当は1本で、実際のローカル読取りツールから親への結果返却まで通った。
- 2担当が独立案を作り、相互批評1往復後に親が企画書へ取りまとめた。第三の担当やOpusの参加、Web担当による最終案の再承認は行っていない。
- 最終worker-releaseは自動承認審査で一度拒否された。実際のsettlementと外部端末の保持条件を再確認し、同じ正式な承認経路で一度の再審査後、保持結果と最終DeliveryのACKが成立した。未ACKとreclaimableは各0件。端末を別経路で閉じる回避はしていない。
- 検証用Web生成を端末指定の正式なinterruptで1回中断し、同じセッションで新しいfixture読取りと最終回答が返ることを確認した。実行記録の`turn_aborted`と次の`task_complete`を区別して検証し、最後にHTTP/Webの処理件数が各0へ戻った。中断した依頼の自動再送は行っていない。

既存端末を`worker-start --terminal`で採用した場合、`launch.requested`/`launch.effective`のモデル欄はnullだった。
この欄だけからモデルを判断せず、端末ヘッダーと当該セッションの実行コンテキストを別に確認する。
`worker-list`の監視情報が`missing_status`、`worker-read`が`session_not_reported`で端末出力へフォールバックする場面もあった。
今回の往復成功は、Orcaの全監視機能が正確にモデルの実行状態を把握できることまで保証しない。
`tui-idle`もモデルとツールの間で真になる場面を観測したため、その値だけで依頼完了や終了可能と判断しない。
Taskの完了通知や当該セッションの`task_complete`と照合する。停止試験後の最終文にはMarkdownによるアンダースコアのエスケープがあり、回答の意味と実ツール出力は確認したが、プレーンテキストのバイト単位一致は保証していない。
既存設定由来のMCP接続警告も観測したが、fixture用のシェル実行は成功した。
この試験だけで他のMCP接続が正常だとは扱わず、無関係な個人設定を変更して解消したことにしない。

## 構成

Orcaが仕事の配分・連絡・終了状態を管理し、各CLIが自分のツールと認証を使う。
現在は通常のCodex/Astraを親、Codex経由のGPT-5.6 Pro Webを子とする。Claude/Opusは任意の後続工程。
Web担当は最初は1本。Pi、Council、別gateway、別タスクキューは追加しない。

Windowsの公式安定版を利用し、RC版への切替やWSL・SSHは初回の対象に含めない。
既存のCodex homeを使用する。Orca追加アカウントの別homeは、Webブリッジのrollout検査と別途照合が必要。
モデルは起動ごとに指定し、ユーザーの全体の既定モデルを変えない。
Orcaの `launch.requested` と `launch.effective`、CLIの実効モデルの証拠を保存する。
既定値への無言のフォールバックや新規の有料契約・API課金への切替は行わない。

## 段階的な確認

1. 使用するCLIのバージョン、正式な認証状態、利用可能な対象モデルを確認する。本人ログインが必要な接続先は保留する。
2. Orcaの通常ターミナルで各CLIを単独起動する。検証専用の小さな作業フォルダーを使う。
3. 安定版にオーケストレーション機能があることを確認する。今回の版は保存設定に旧Experimentalキーがなくても正式なAPIが動作した。画面で設定を切り替えたという記録にはしない。
4. 同梱の `orca skills get orchestration --full` を読み、現在のRun、Task、Dispatch、Deliveryの手順に従う。
5. Astraを親、Webを子にして、指定ファイルの読取り、結果報告、追加質問を一往復行う。Opusの導入後は、その単独利用とAstraとの両方向の委譲を別途確認する。
6. 停止・失敗が親に届き、別の担当を止めないことを確認する。送信済みか不明な仕事を自動再実行しない。
7. WebのGPT-5.6 Proを1担当として起動し、実効モデル、ツール呼出し、2通目、完了、停止後の新規依頼を確認する。

Runを作っただけでは自動的に仕事は配分されない。親がworker-startとメッセージ受信を進める。
完了は起動時に返されたtaskIdとdispatchIdに結び付ける。廃止されたrun/coordinator-start系のコマンドを使わない。
安定版の機能不足、モデル利用資格不足、認証待ちは、それぞれ独立した未完了理由として残す。

### Windowsでの起動と承認

Orcaから起動するCodexの保存先を起動時に確認する。必要なら子プロセスの`CODEX_HOME`だけに既存の保存先を指定し、モデルと推論量も実行単位で明示する。
カスタム設定を持つ既存端末は、正式な`worker-start --terminal`で採用できる。新しいTask/Dispatchを作り、前の依頼の識別子を再利用しない。

この環境ではCodexのWindowsサンドボックスからOrca CLIへの実行権がなく、最初の試行はRun作成前に失敗した。
対応したCodex CLIの`--approve-for-me`を使い、個々の操作を正式な自動承認審査へ送ることで通信試験を進めた。サンドボックスの無効化やACLの書換えは行っていない。
審査は常に許可されるとは限らない。拒否された操作を別の実行経路へ移して続けず、状態を保存して判断を待つ。
Orca CLIはインストールされたネイティブ実行ファイルの絶対パスを指定する。今回の初回Web報告だけはbare `orca`の解決先を独立確認できず、以後の依頼に絶対パスの条件を追加した。

### 完了通知と後処理

同梱の版に対応する手順に従う。正しい`worker_done`をOrcaが受け入れるとTask/Dispatchが確定する。その確定と、親が通知を受領したというDeliveryのACKは別の状態。
結果と識別子を確認し、担当を再利用・保持・解放する判断を行ってから通知をACKする。プロセス終了はさらに別に確認する。
外部の既存端末を採用した場合、公式の`worker-release`は端末を保持する。解放APIの成功だけで端末やモデルプロセスが終了したとは扱わない。
`accepted: true`だけでは依頼開始を意味しない。送信の受領、実際の開始、完了通知、プロセスの状態を分け、応答が不明な依頼は自動で二重送信しない。

## 企画検討のひな型

議題は検証専用の「小さな航海ゲームの序盤30分」。実作品の資料やコードを使わず、ローカルに保存する。

- 共通条件: 一人制作の小規模試作、2D、戦闘なし。小さな港3つ、航海・発見・交易を中心とする。最初の30分でプレイヤーが行うことを具体化する。
- Astra: 進行と取りまとめ。初回に企画案を作り、批評を受けて修正する。
- Opus（今回は保留）: 将来追加する場合は、プレイヤー視点の批評。単調さ、理解しづらさ、意思決定がない時間、企画の矛盾を指摘する。
- GPT-5.6 Pro Web: 独立した別案、制作規模、試作で検証する項目を提案する。

初回の評価は独立して行う。親が成果を交換し、論点を指定した相互批評を最大2往復行う。
各担当の文書は別ファイルにし、最終決定記録は親がまとめる。
成果には採用案、プレイヤーの行動、反対意見の扱い、却下案と理由、未解決事項、試作仮説、次の作業を含める。
各担当の実出力がそろわない場合は、議論完了や合意が成立したと記載しない。
今回はAstraとWebが互いの案を批評した。親が作る最終案は、全員が再承認した合意案とは区別する。
実際の依頼・返答・個人設定はローカルだけに保存し、公開リポジトリには一般化した手順と確認範囲を記録する。
