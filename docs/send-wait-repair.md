# 起動時に本文を入力したまま送信しない問題

調査・修正日：2026-09-27。修正版：6.1.1-fork.5（未配布のfork.4に追加修正）。

## 原因

ランチャーの `RequestCoordinator.acquire("send")` が生成 POST の制限に加えて、
会話情報取得の `conversation` 制限も参照していた。別タブの背景 GET が429になると、
準備済みのプロンプトまで共有のバックオフに巻き込まれる。制限が繰り返されると
バックオフは30、60、120、240、300秒と増えた。

実ログでは `e83af4b9e3d9` が23:44:11 JSTに添付準備を完了後、
`intent=send / reason=rate-limit / remainingMs=295719` で待機した。
23:49:07に再開し、送信受付自体は3360msで確認できた。
`2a9ac086756e` も23:54:19に `remainingMs=294503` で待機した。
この間はクリック自体が実行されていないため、送信ボタンのクリック再試行では直らない。

待機イベントは通常ターンでは `onPreparationProgress` が接続されず、Codexへの
説明が表示されなかった。ランチャーの再試行時刻もツールチップだけにあった。

## 修正

- 準備済み送信は生成の制限だけを参照する。会話情報の制限はページを開く処理に適用する。
- 生成の429、Retry-After、送信間隔、所有タブの不明な制限による待機を維持する。
- 通常ターンにも待機・再開のcommentaryを接続。3秒未満の間隔調整と同じ予定の反復通知は表示しない。
- 待機中タブのラベルにも次回試行時刻を表示する。
- 送信操作・送信済み判定・再送の安全境界は変更しない。

## 確認

関連ランタイムテスト83件、ランチャーの調整処理テスト9件、型チェック、UIビルド成功。
通常の非圧縮ターンから待機と再開がcommentaryとして出る統合テストを含む。
利用者の指示により追加の長い実送信検証は実施しない。
最終配布物と反映状況は `output/turn-repair-20260927/` に記録する。

## 再起動後の停止への追加修正

再起動後も稼働版はfork.3で、先に準備した待機修正は未反映だった。

- 本編の最新停止は `Compaction continuation requires one current native environment claim (found 2 distinct claims in 2 envelopes)`。
  XML全文の一致を要求していたため、日付・サブエージェント一覧の更新も別権限と判定していた。
  全候補の作業フォルダー、ルート、権限を現ターンの正式なrolloutに照合するよう変更。
  省略されたcwd/rootを補うのは厳密な形式の日付・無制限プロファイル更新だけで、
  不一致の権限、別フォルダー、壊れたcwd、正式記録のない継続は引き続き拒否する。
- `preflight-effort` の単発読取を最大1秒の中断可能な安定待ちに変更。
  メニューを閉じた直後のラベル・編集可否の更新遅れを許容し、恒久的な不一致は拒否する。
  過去の失敗時DOMは保存期限外のため、この競合が当該画像の唯一の原因とは未確定。
- この修正チャットのtrace `e97f507493c4` は送信が受理された後、
  2026-09-27 00:54:39 JSTに `ChatGPT prompt attachment aborted` で終了した。
  6回の生成要求は200で、9回の会話情報取得が429だった。502は橋渡し側の変換結果であり、
  ChatGPTからHTTP502が返った証拠ではない。既知のセッション取消は499/client_cancelledを保持する。
  当該中断の発生元までログで確定できておらず、すべての送信後停止を解消したとは扱わない。

追加検証は環境情報89件、変更箇所の限定テスト15件（環境情報12件を含む）、
日本語Proモデルのブラウザーfixture2件、型チェックと配布ビルド。
実サービスで長時間の生成・停止した本編の再開は行わない。

## 6分割と所要時間

通常ターンは入力全体の量と送信上限に応じて1・2・6分割を選択する。
履歴圧縮は現行設計で6分割固定。ここは今回変更していない。
上記traceは推定214,635入力トークン、multipart-6。
画面の最後の依頼文の短さだけでは送信量は決まらない。
ステージ4の受領待ちは3,070ms、ステージ5は3,432msだった一方、
送信スケジューラーには会話情報429による数分の待機が入っていた。
待機修正は各分割にも適用するが、実際の生成429や受領応答待ちは維持する。

## 別件のWebモデル非対応エラー

「Webモデルのエラーを修正」の23:46:27 JSTのターンは約1.1秒でHTTP 400となった。
この調査で確認した現在のCodex設定はローカル `/v1` に接続し、モデルキャッシュには
`chatgpt-web/gpt-6-pro` が表示対象として存在する。元ターンの実際の接続先は未確認であり、
このエラーを今回の待機修正で解消したとは扱わない。
