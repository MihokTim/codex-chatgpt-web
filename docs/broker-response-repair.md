# Windowsの内部通信における応答確定と終了待ち

対象: `6.1.1-fork.8`。公開APIとbrokerの通信形式は変更しない。

## 再現した問題

通常のbroker要求は、改行で終わる完全な応答を受け取っても接続の物理的な終了を待っていた。
Windowsの名前付きパイプで相手を開いたままにすると、成功の結果も具体的なエラーも
`ChatGPT web turn broker timed out` に置き換わった。修正前の独立した2ケースで再現した。
これは内部通信の弱点の再現であり、過去に報告されたWeb停止すべての原因の確定ではない。

## 変更

- 通常要求も、要求IDが一致する完全な応答フレームで結果を確定する。
- 通常要求の通知はBunのパイプコールバックを抜けてから行う。既存の無期限long-pollの通知順序と終了処理は維持する。
- 通常要求では相手の終了を受け入れ、結果確定後に相手が閉じない場合の接続破棄は別の1秒の猶予で行う。
- brokerの終了は、受け入れた接続のcloseを待ってから待受サーバーを終了する。WindowsのBunが応答を書き込み中の終了と競合することを防ぐ。
- 受信終了までに完全なフレームがなければ失敗する。null・配列・不正なerror型も明示的に拒否する。
- 要求の再送、ツール再実行、モデルの切替、完了フェンスの省略、cleanupエラーの黙殺は追加しない。

## 検証

`tests/turn-broker-response-frame.test.ts` で、接続終了の遅延、サーバーエラーの保存、
キャンセル、不完全・不正応答、UTF-8の分割受信、大きな応答、子プロセスの終了、
同じパイプでの30回の終了・再起動を検証する。

変更途中の単純な即時終了案では既存のDEVツール継続試験でBunのクラッシュが起きたため採用せず、
接続終了の待機と既存long-pollの扱いを含めた修正を最終検証の対象とする。
関連試験はWindows上のファイル単位の別プロセスで実行する。

2026-09-27のローカル確認では、関連14ファイル284件、分割送信の11ケース、
fork識別の11件が成功した。分割送信のファイル一括試験は外側の180秒制限で中断したため、
完了済み8ケースに加え、2分割・6分割・重複ACKを選択して別プロセスで確認した。
その一括実行自体を成功とは扱わない。DEVのリモートowner終了処理は15プロセス連続でも成功した。
型チェック、launcherの型チェックとビルドも成功した。実送信とインストール結果は別の確認を要する。

反映は処理中件数ゼロとランチャーのidleを確認してから行う。配布先と実効runtimeの
manifest、プロセス所有関係、モデル取得、GPT-5.6 Proでの実送信を別々に確認する。
最終の試験・配布結果は、作業環境の `output/broker-orca-20260927` に保存する。

参考にした差分: [omarcosr/codex-chatgpt-webの応答確定修正](https://github.com/omarcosr/codex-chatgpt-web/commit/cbed4a53aad4df131426c85fc555f575efc86edc)。
同コミットのcleanupエラー表示の変更は取り込んでいない。
