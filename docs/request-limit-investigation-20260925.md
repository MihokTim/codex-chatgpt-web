## 判断

最初に直すのは「何の通信が制限されたかを区別できないこと」。続いて、確認できた重複通信を減らし、制限対象の新規送信を待機させ、途中まで受理された分割送信を保全する。5タブ上限の引き上げや、全体の並列生成の停止を先に行う根拠はない。

OpenAI側の上限自体をブリッジから解除できるとは言えない。一方、ブリッジによる余分な通信や送信集中が原因なら、その発生頻度は改善できる。公式の[ChatGPT Pro説明](https://help.openai.com/en/articles/9793128-about-chatgpt-pro-tiers)は一時的な利用制限があり得ると説明しているが、今回の会話アクセス制限の具体的な閾値や原因を説明する資料ではない。

## 実装順序

### 1. 制限の根拠を記録し、画面表示とHTTP拒否を分ける

- 既存のブラウザー通信イベントを使い、追加のHTTPリクエストなしで観測する。
- 記録項目は時刻、所有タブ、trace、作業段階、HTTPメソッド、通信カテゴリ、status、Retry-After、受理確認の有無。カテゴリは生成、会話参照、認証、その他などの固定値とし、任意URLをそのまま保存しない。
- Cookie、Authorization、本文、クエリ文字列、会話IDやアカウントIDを含むパスは記録しない。通常通信は集計中心、制限時だけ直前の短い履歴を残す。
- ダイアログのみの検出は「画面で制限検出・対象通信不明」と明示する。互換性のため既存statusを保持する場合も、上流HTTP応答が確認済みと誤解されない証拠種別を添える。
- 生成POSTの拒否は、当該ページで当該Sendから発生したrequestとresponseを照合する。既存413検出observerの所有範囲の考え方を利用し、別タブの応答を混ぜない。
- 保守ページの制限表示だけを理由に、正常に進んでいる別タブを終了しない。ただし表示を閉じたことを制限解除の証拠にも扱わない。

変更候補：`browser-worker.ts` の制限検出とsubmission observer、`adapter-error.ts` とhelperのエラー伝達、`browser-host.cjs` の通信監視。

注意：Electronの既存 `webRequest.onCompleted` はCloudflare対応にも使用している。別の登録で上書きしない。既存監視に統合するか、Playwrightのresponseイベントで分離する。保守ページと作業ページを識別し、生成ストリーム終了まで待たず拒否応答を観測できる構成にする。

### 2. 補助通信の重複を減らす

- `/api/auth/session` のSendごとの取得を削減候補にする。短時間の分割送信に必要なアカウント確認を、同時取得の共有と有効期間を限定した再利用にまとめる設計を検証する。
- アカウント切替、ログアウト、認証状態の変化、確認失敗時の無効化が必要。別アカウントへ利用量を誤計上しないことを優先し、確かな本人性を確認できない場合は追跡欠落として扱う。
- 同時呼出しの共有だけでは逐次6回の取得は減らないため、再利用条件もテストする。各物理Sendの利用量receiptは維持する。
- 保守画面のreloadやセッション確認も、手順1で実際の頻度と発火元を確認し、重複しているものだけ整理する。認証が必要な操作やモデル選択の確認を一律に省略しない。

変更候補：`limits.ts`、`browser-worker.ts` の `usageSubmission`、必要に応じてランチャーのセッション状態管理。

### 3. 制限時の待機と途中再開を整える

- 実際に制限されたカテゴリを根拠に、新規送信・新規タブ作成を待機させる。複数helperとコンテキスト圧縮経路で共有できる調整を使い、各helperが独立して再試行を集中させない。
- Retry-Afterが確認できた場合はそれを尊重する。なければ上限のある段階的な待機にし、解除時の同時送信も避ける。待機中はキャンセル可能とし、待機理由と次の判定時刻を既存の状態・進捗経路で表示する。
- すでに受理された生成は観測を継続する。送信済みか不明なものを再送しない。受理の証拠、分割ACK、conversationの同一性、送信内容の同一性を保持する。
- 「未送信」または「当該送信の拒否」が確認できる場合のみ、その未受理部分からの復旧を検討する。6/6の失敗で1/6から送り直すことはしない。再開条件を満たせない場合は明確な中断状態と根拠を返す。
- UIのみの制限は対象不明として保守的に扱い、無条件で無視したり、retryableをtrueにするだけの変更は行わない。
- 正常な生成を一律直列化せず、短時間の送信集中を制御する。固定5タブの制約と送信頻度は別の設定・状態として扱う。

変更候補：ランチャー側の共有状態とhelperプロトコル、`turn-execution.ts`、`browser-worker.ts`。通常実行だけでなくcompaction fallbackも対象とする。

### 4. タブと担当の対応を表示する

- タスクID・担当名を明示的なメタデータとして渡し、「親／担当名」と「送信待機・分割送信中・圧縮中・生成中・完了保持」を表示する。プロンプト本文から名前を推測しない。
- 稼働中タブ、保持中タブ、native担当を区別できる説明を付ける。
- これは状況把握の改善であり、リクエスト制限そのものの解消ではないため、前の3項目を優先する。

## 検証条件

| ケース | 成立させる条件 |
| --- | --- |
| 保守ページだけに制限 | 作業タブで進行中の生成を中断しない。保守ページの問題として記録する。 |
| 生成POSTにHTTP 429 | 当該Sendと紐付き、Retry-Afterと拒否根拠が記録・伝達される。受理済み扱いしない。 |
| ダイアログだけでHTTP根拠なし | 対象不明と分かる。自動的な無制限再送をしない。 |
| 2helperと圧縮が同時に制限 | 共有待機が効き、解除時も集中送信しない。 |
| Retry-After | 秒数・HTTP日付・不正値を扱い、待機はキャンセル可能。 |
| 6分割の途中拒否 | 受理済み段階を再送しない。未受理部分の復旧と、結果不明の中断を区別する。 |
| 認証確認の再利用 | 分割送信で取得回数が減る。同時取得、期限切れ、ログアウト、アカウント切替、確認失敗で誤計上しない。 |
| 既存機能の回帰 | 413検出、Cloudflare対応、モデル確認、6/6送信、完了タブ回収、キャンセルが維持される。 |
| 実環境 | 制限を意図的に発生させる負荷試験はしない。通常利用の受動観測で通信カテゴリ別件数と再発を確認する。 |

変更範囲に対応する契約テストとブラウザー回帰テスト、型検査を行う。実装がランチャー・helper間のプロトコルを変える場合は配布runtimeの検証も必要。稼働中の対象タスクを中断する再起動は避け、反映できる安全な切替時点を別途確認する。通信件数の減少だけで「制限解消」と断定せず、実際の制限再発と復旧成否を確認する。

## fork.7 実装・再調査（2026-09-25）

### 300秒エラーの再調査

採取ログは2026-09-23 12:10:13 JSTから2026-09-25 15:13:52 JSTまでを含む。`ChatGPT compaction did not fully settle within 300000ms` に一致した記録は9月24日12:41:58、21:59:16、22:32:19 JSTの3件。採取範囲の9月25日には同文言は見つからなかった。添付画像には前日の履歴が含まれており、画像だけで9月25日に新規再発したとは断定できない。

一方、9月25日13:56:22 JSTに `20862f6b2ab0_fallback` の1/6が受理され、13:56:37に2番目の入力準備で頻度制限の画面表示が検出されていた。これは新しい中断として確認した。上流HTTPの拒否エンドポイントは、旧版ログからは依然として特定できない。

タイマーは既に最終送信受理後に停止する実装だったが、最後の分割ACK通知が遅れて届くと再起動できる経路があった。生成開始を状態として確定させ、後着のACK・準備進捗で準備タイマーを再起動しないよう修正した。準備・生成・後処理の段階と、最後に進んだ操作を期限切れログに記録する。準備中の明確な待機は別枠で有限に扱い、単なるheartbeatでは期限を延長しない。

また、分割ACK待ちにも頻度制限の確認を追加した。制限表示や当該送信のHTTP拒否を観測しているのに、ACK待ちの期限全体を消費して一般的なタイムアウトになる経路を防ぐ。
